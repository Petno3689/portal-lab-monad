# ТЗ — «Лаборатория нестабильных порталов» на Monad

Целевая спецификация ончейн-версии. Парная к `CLAUDE.md` (конституция и «почему»);
здесь — «что и как». Читается новым чатом вместе с `CLAUDE.md`. **Код целевой
версии написан** (контракт, TS-зеркало, векторы, тесты); этот документ —
спецификация, а текущий статус — в `docs/STATUS.md`.

**Версия 2.** Переписана после инженерного разбора: старение считается формулой,
у действий появилась цена, добавлены типы порталов, уточнена интеграция с Pyth,
зафиксирована арифметика.

---

## 1. Обзор

Ончейн-выживалка на тестнете **Monad**. Игрок-смотритель управляет порталами
(разведка, стабилизация, дестабилизация, спасение, эвакуация, закрытие) в реальном
времени и старается продержаться как можно дольше. Вся игровая логика и состояние —
в смарт-контракте; клиент читает состояние и шлёт действия транзакциями. Счёт —
прожитые игровые часы; результат попадает в ончейн-лидерборд.

---

## 2. Целевая архитектура

```
┌──────────────────────────┐   tx (действия, settle)   ┌───────────────────────┐
│  Клиент (React + viem)   │ ────────────────────────▶ │  Контракт игры        │
│  - переиспользует UI     │ ◀── чтение state/события ─│  (Solidity, Foundry)  │
│  - session-key (burner)  │                           │  - домен на Solidity  │
│  - локальная проекция    │                           │  - лидерборд          │
│    времени (та же        │                           └───────────┬───────────┘
│    арифметика!)          │                                       │ request/callback
└──────────────────────────┘                                       ▼
                                                        ┌───────────────────────┐
                                                        │  Pyth Entropy V2      │
                                                        │  (ончейн-рандом)      │
                                                        └───────────────────────┘
```

- **Сервера игры нет.** Авторитет — контракт.
- **Зависимости:** контракт Pyth Entropy на тестнете Monad; viem/wagmi на фронте;
  Foundry в разработке.
- **Индексация:** для v1 фронт читает состояние по RPC, слушает события и локально
  досчитывает деградацию между чтениями. Индексер (Ponder/subgraph) — позже, если
  событий станет много.

### 2.1. Ключевой инвариант

> **Всё, что происходит без игрока, обязано быть вычислимым по снимку и часам.**

Из него следуют три решения этого документа: старение — формула (§5), длинная
пауза — детерминированное переполнение (§5.5), арифметика — одинаковая в контракте
и во фронте (§4.1). Нарушение инварианта в любой точке означает, что экран врёт до
следующей транзакции.

## 3. Модель данных

В storage — только **живое** состояние. История — в событиях (§9).

### 3.1. Portal

- `id`, `portalType` (uint8, см. §4.5), имя/мир — индекс в пуле имён (`uint8`);
- `status`: `empty | open | questioned` — **отдельного статуса «закрыт» нет**
  (см. ниже);
- `surveyed: bool`;
- `narrowedOnce: bool` — первая (неточная) разведка глухого портала сузила
  диапазоны; следующая разведка читает точные значения (см. ниже);
- `creaturesKnown: bool` — точное число существ известно (см. ниже);
- **параметры-диапазоны** (пока не разведан): `energyLo/Hi`, `stabilityLo/Hi`,
  `creaturesLo/Hi`;
- **точные параметры** (после разведки): `energy`, `stability`, `creaturesInside`;
- **`hoursToCollapse` — точное и публичное всегда**, даже до разведки;
- `observerSent`, `rescuerSent` — кто внутри;
- `spawnedAtHour`, `snapshotAt` — момент последней фиксации параметров;
- `surveyPending: bool` — разведка запрошена у Pyth, ждём колбэк.

> **`creaturesKnown` vs. `surveyed`.** Точная разведка выставляет оба флага сразу.
> Но **слепое спасение** (§4.2 Решение 6) даёт спасателю узнать точное число существ
> **без** полной разведки: заход вслепую бросает число и ставит `creaturesKnown =
> true`, а `surveyed` остаётся `false`. Поэтому флаги разнесены и **не
> взаимозаменяемы**: стоимость закрытия (§4.4) и схлопывания (§5.6) читают
> `creaturesKnown`; полнота эвакуации (§4.2, «один в темноте») и осторожная оценка
> риска (§4.2 Решение 5) читают `surveyed`. Не «выравнивать» — разрыв load-bearing.

> **Диапазоны вместо тумана.** Пока `surveyed=false`, истинного значения **не
> существует** — есть публичный диапазон. Разведка бросает Pyth-жребий внутри
> текущего диапазона и записывает точное значение. Это единственный
> ончейн-честный способ «скрытой» информации: storage читается кем угодно.
> Диапазон со временем **расширяется в обе стороны** — ранняя разведка тактически
> ценна.

> **Время до схлопывания диапазоном не прячется.** `hoursToCollapse` хранится
> точным и публичным с момента появления портала, а не как `hoursLo/Hi`. Иначе
> момент схлопывания неразведанного портала не определён, а формула ленивого
> времени (§5) обязана вычислять его из снимка для любого портала. Диапазонами
> закрыты только энергия, стабильность и число существ.

#### Разведка (тикет 1.7)

Отправка наблюдателя (`SendObserver`) в неразведанный портал **есть** разведка.
Со **заглушкой-рандомом** (Веха 1, см. §6.6) ответ синхронный: `surveyPending`
после действия всегда `false`; двухфазность (request → callback) появится вместе
с настоящим Pyth на Вехе 4. Счётчик бросков `Game.rngNonce` увеличивается на
единицу при каждом обращении к разведке (до бросков), чтобы повторный заход давал
другой результат.

- **Обычные типы (`surveyPrecise = true`).** Разведка бросает жребий внутри
  текущего диапазона каждого параметра (энергия, стабильность, число существ) и
  записывает точное значение; диапазон **схлопывается в точку** (`lo = hi =
  значение`), иначе в структуре остались бы два противоречащих источника правды.
  `surveyed = true`.

- **Глухой тип (`surveyPrecise = false`, Решение 2).** **Первая** разведка не
  даёт точного значения: каждый из трёх диапазонов лишь **сужается вдвое**
  вокруг случайной точки внутри него (новая полуширина `w = (hi − lo + 1) / 4`,
  новые границы `[c − w, c + w]`, обрезанные исходными `lo`/`hi`), портал
  помечается `narrowedOnce = true`, а `surveyed` остаётся `false`. **Вторая**
  разведка помеченного портала читает точные значения, как у обычного типа, —
  внутри суженных (и успевших расшириться) диапазонов; диапазоны схлопываются в
  точки, `surveyed = true`. Между заходами нужно отозвать наблюдателя и отправить
  снова — ещё ресурс, ещё время. Это и есть цена типа «глухой»: без неё он был бы
  обычным порталом с другим названием. Порога ширины нет: измерено, что при
  обычном темпе игры диапазоны расширяются на 2 в час между разведками, и
  портал с порогом был практически нечитаем.

> **Почему разведка тайминг-чувствительна.** Диапазон со временем расширяется
> (см. ниже), поэтому ранняя разведка тактически ценна: узнать точное значение,
> пока оно ещё узкое.

#### Порча знания со временем (Решение 3)

Пока портал не разведан, его диапазоны **энергии и стабильности** со временем
**расширяются в обе стороны**: каждая граница уходит наружу на
`rangeWidenPerHour` единиц за игровой час (пол 0, потолок 100). Знание портится —
чем дольше не смотришь, тем меньше известно. Считается той же формулой ленивого
времени (§5), без цикла по часам: сдвиг = `rangeWidenPerHour × e`, где `e` —
прошедшие игровые часы.

> **Диапазон числа существ НЕ расширяется — ни за какое время.** Неограниченно
> растущий диапазон существ раздувал бы штраф за закрытие вслепую (§4.4, берётся
> середина диапазона) до абсурда: чем дольше отсутствие, тем дороже вслепую
> закрыть. К тому же число обитателей задано **природой** портала, а не давностью
> наблюдения. Расширяются только энергия и стабильность.

> **Разведанный портал диапазонами не пользуется** — после разведки истина в
> точных полях `energy`/`stability`/`creatures`, а поля-диапазоны равны им и не
> трогаются старением.

> **Закрытие и схлопывание освобождают слот.** Порталы — фиксированный массив из
> 12 элементов; закрытый или схлопнувшийся портал не превращается в запись со
> статусом «закрыт», а обнуляет свой слот до `empty`. Живой истории в storage нет
> — она уходит в события (§9).

### 3.2. Game (партия игрока)

- `player`;
- `startedAt`, `lastTickAt` — база для расчёта времени;
- `hoursElapsed` — прожито игровых часов (основа счёта);
- `hp` — шкала жизней, старт `HP_START` (≤ `HP_MAX`);
- `power` — ресурс лаборатории (§4.3);
- `observersFree`, `rescuersFree` — свободный штат;
- `portals[]` — живые, ≤ `MAX_OPEN_PORTALS` (12);
- `spawnDebt` — накопленное давление спавнов;
- `finished`, `diedAtHour` — итог партии.

Одна активная партия на адрес: `mapping(address => Game)`.

### 3.3. Leaderboard

- `mapping(address => uint) bestHours` — личный рекорд;
- событие на каждую фиксацию; полная таблица строится с фронта по событиям.

### 3.4. Параметры деплоя (immutable)

Задаются в конструкторе, после деплоя не меняются:
`SEC_PER_HOUR` (старт **15**), `HP_MAX`, `HP_START` (стартовое здоровье, ≤ `HP_MAX`),
`POWER_MAX`, `POWER_REGEN`, стоимости действий, таблица типов порталов, коэффициенты
сложности, `LONG_ABSENCE_HOURS`.

> **Ограничителя спавнов на транзакцию нет.** Поле `maxSpawnsPerTx` удалено: портал
> рождается в час, когда созрело его давление, кто бы и когда ни вызвал приведение
> (§5.3, §7). Конструктор отвергает `hpEmptyCollapse = 0`
> (`InvalidConfig("hpEmptyCollapse")`): на том, что каждое схлопывание стоит HP,
> держится оценка числа событий одного догона (§5.3).

> **`HP_START` — главный рычаг длины партии.** Стартовое здоровье отделено от потолка
> (`HP_MAX`) специально. `HP_MAX` определяет, сколько можно набрать через спасение.
> `HP_START` определяет, с каким запасом прочности игрок входит в игру: чем ниже —
> тем короче средняя партия и агрессивнее нужна стратегия с первых часов.

> **Как реализованы «неизменяемые».** Не ключевым словом `immutable`, а
> **хранилищем без сеттеров**: конфигурация — структура `Config` плюс таблица
> `PortalTypeParams[5]`, записанные один раз в конструкторе, менять их
> нечем. `immutable` не годится — параметров около шестидесяти плюс таблица типов,
> а `immutable` не работает со структурами. На Monad это ещё и дёшево: конфигурация
> лежит в storage подряд и читается за одно холодное обращение (страницы по 128
> слотов, §14.1). Владельца, способного что-то поменять на живом контракте, нет.

> **Почему immutable, а не изменяемые владельцем.** Эти числа участвуют в расчёте
> **прошлого**: изменение темпа посреди партии пересчитает уже прожитую историю и
> сломает её. Плюс изменяемый параметр вводит владельца, способного менять скорость
> игры всем — ровно ту доверенную сторону, от которой уходит пивот. На тестнете
> передеплой ничего не стоит.

## 4. Игровые правила

### 4.1. Риск — фиксированная точка, канон Solidity

- `surveyed=false` → уровень `unknown`, счёт не считается.
- `closed` → счёт 0.
- Иначе: база из трёх взвешенных компонентов (нестабильность 0,5; энергонагрузка
  0,3; дефицит времени 0,2), затем последовательные факторы, каждый из которых
  приближает риск к сотне на свою долю: `риск = риск + (100 − риск) × k`.
- Пороги уровней: 0–29 low, 30–59 medium, 60–84 high, 85–100 critical.

**Алгоритм по шагам (канон, реализован в `RiskLib.sol`).** Масштаб `S = 1e18`,
деление половины вверх `divHalfUp(a, c) = (a + c / 2) / c`. Порядок операций и
округлений — часть спецификации: от него зависит побитовое совпадение с
TS-зеркалом. Входы: `stability` (0..100), `energy` (0..100), `hoursToCollapse`,
`lives` (живые внутри = существа + наблюдатель + спасатель).

1. `inst = (100 - stability) * S`
2. `en = energy * S`
3. `tp = hoursToCollapse >= 48 ? 0 : 100*S - divHalfUp(hoursToCollapse * 100 * S, 48)`
4. `r = divHalfUp(inst*50 + en*30 + tp*20, 100)` — база, веса 0,5 / 0,3 / 0,2.
5. фактор времени (взаимоисключающие ветки):
   - `hoursToCollapse <= 2`: `r = r + divHalfUp((100*S - r) * 45, 100)`;
   - иначе `hoursToCollapse <= 6`: `r = r + divHalfUp((100*S - r) * 20, 100)`.
6. если `stability < 20`: `r = r + divHalfUp((100*S - r) * 35, 100)`.
7. если `lives > 0`: `k = min(30, 8 + 4*lives)`,
   `r = r + divHalfUp((100*S - r) * k, 100)`.
8. `score = divHalfUp(r, S)`, не больше 100.

**Арифметика:**

- все промежуточные значения — в фиксированной точке **10^18**;
- деления — с округлением **половины вверх**, не отбрасыванием;
- переполнение невозможно: максимум промежуточных значений ~10^21 при потолке
  `uint256` ~10^77;
- **канон — целочисленная реализация.** Ревьюер смоделировал этот алгоритм и
  сравнил с прежней дробной версией на **776 286 комбинациях входов — ни одного
  расхождения**. Точности 10^18 хватает с запасом. Поэтому старые числовые
  ожидания из `../portal-lab/src/test/risk.test.ts` на этой сетке остаются верными, но канон —
  именно целочисленная версия, а не эти числа.

**Контракт возвращает только балл и уровень.** Раскладку по факторам (сколько дали
нестабильность, энергия, время, живые) он не считает: она нужна только UI, а её
подсчёт на цепочке стоил бы газа без пользы для контракта. Раскладку даёт
TS-зеркало (§4.1, тикет 1.3).

**Зеркало на TypeScript обязательно.** Реализация на BigInt, побитово
воспроизводящая контрактную. Находится в `shared/src/risk.ts` (пакет `shared/`,
позже импортируется фронтом на Вехе 6). Используется фронтом для локальной проекции
и служит независимой сверкой.

**Три вида тестов:**

1. **Поведенческие** — смысл 45 существующих тестов: какой уровень, какое действие
   разрешено, в какую сторону двинулся риск. Без привязки к точным числам.
2. **Граничные** — прицельно 29/30, 59/60, 84/85. Там переключаются ворота
   (критический риск запрещает отправку людей), и ошибка в единицу меняет поведение
   игры. В старом наборе таких тестов нет.
3. **Сравнительные** — тысяча случайных состояний портала через Solidity и через
   TS-зеркало, сверка побитово. Любое расхождение — баг с конкретным входом.

**Инфраструктура сравнительной сверки (эталонный файл).**

Для сравнительных тестов используется эталонный JSON-файл
`shared/test/vectors/risk-vectors.json`. Он **генерируется один раз** скриптом
`contracts/script/GenRiskVectors.s.sol`, который вычисляет векторы через настоящий
`RiskLib` и закрепляется в git. Оба набора тестов читают этот файл:

- `contracts/test/RiskGolden.t.sol` (Foundry) — проверяет, что `RiskLib`
  воспроизводит каждую строку файла;
- `shared/test/risk.golden.test.ts` (Vitest) — проверяет, что TS-зеркало
  воспроизводит каждую строку файла.

Если обе сверки зелёные — реализации совпадают друг с другом побитово.

**Почему не `ffi`.** `forge test --ffi` требует разрешения на запуск внешних
процессов и отключено: изолированный прогон тестов не должен зависеть от Node.js.
Промежуточный файл — это подтверждённый контракт между двумя реализациями.

**Почему параллельные массивы, а не массив объектов.** `vm.parseJson` в forge-std
декодирует поля по алфавитному порядку ключей, а не по порядку объявления —
известная ловушка. Параллельные массивы читаются через `vm.parseJsonUintArray` без
сюрпризов.

**`breakdown` обязан приходить к тому же баллу, что `score`.** Зеркало содержит
функцию `breakdown(p: PortalLike): RiskBreakdown` — подробную раскладку по
факторам для панели «Как посчитан риск». Раскладка пошагово повторяет те же
вычисления, что и `score`, и финальное значение `steps[2].after` должно
удовлетворять инварианту: `min(100, divHalfUp(steps[2].after, S)) === score(...)`.
Иначе панель объясняет не тот риск, который показан игроку.

### 4.2. Действия и отказы

Девять действий (порядок задаёт integer-значение enum `Action` в
`PortalLabTypes.sol`):

| # | Идентификатор | Суть |
|---|---|---|
| 0 | `ToggleQuestioned` | Переключить статус «под вопросом» |
| 1 | `Stabilize` | Поднять стабильность |
| 2 | `Destabilize` | Снизить стабильность (открывает закрытие) |
| 3 | `SendObserver` | Отправить наблюдателя (запускает разведку) |
| 4 | `RecallObserver` | Отозвать наблюдателя |
| 5 | `SendRescuer` | Отправить спасателя |
| 6 | `RecallRescuer` | Отозвать спасателя |
| 7 | `Evacuate` | Эвакуировать существ (даёт HP) |
| 8 | `Close` | Закрыть портал |

**Проверки живут в контракте** (`RulesLib.check`), а не только в UI: отказ
нельзя обойти. `canAct(player, slot, action)` — публичная read-функция для фронта.

#### Эффекты действий (`EffectsLib`, тикет 1.5)

Действие применяется **только после** успешной проверки. Сила стабилизации и
дестабилизации зависит от типа портала: `mult = actionMultiplierPct` из
`PortalTypeParams` (100 — обычный, 200 — резонансный).

| Действие | Эффект |
|---|---|
| `ToggleQuestioned` | `Open` ↔ `Questioned` |
| `Stabilize` | стабильность `+= 25 × mult / 100`, потолок 100; энергия `−= 10`, пол 0 |
| `Destabilize` | стабильность `−= 25 × mult / 100`, пол 0; энергия `+= 10`, потолок 100 |
| `SendObserver` | `observerInside = true`; `observersFree−−`; если не разведан — `surveyPending = true` |
| `RecallObserver` | `observerInside = false`; `observersFree++` |
| `SendRescuer` | если `creaturesKnown`: `rescuerInside = true`; `rescuersFree−−`. Иначе **слепой заход** (§4.3): бросок числа существ, `creaturesKnown = true`, диапазон схлопывается в точку; при `> 0` — обычный вход; при `0` спасатель **не входит**, `rescuersFree−−` и уходит на восстановление |
| `RecallRescuer` | `rescuerInside = false`; `rescuersFree++` |
| `Evacuate` | `saved = surveyed ? creatures : (creatures > 0 ? creatures − 1 : 0)`; `creatures −= saved`; `rescuerInside = false`; `rescuersFree++`; `hp = min(hpMax, hp + healPerCreature × saved)` |
| `Close` | см. §4.4 (погибшие, штраф HP, обнуление слота) |

> **Деления в эффектах — с отбрасыванием (округление к нулю), в отличие от
> арифметики риска (§4.1, половина вверх).** Точность здесь не нужна, а
> отбрасывание проще и дешевле. Не «исправлять» на округление.

#### Порядок проверок (первое совпадение выигрывает)

1. **Партия активна** (`startedAt ≠ 0 && !finished`) → иначе `GameNotActive`.
2. **Слот в диапазоне** (`slot < 12`) → иначе `InvalidSlot`.
3. **Слот не пуст** (`status ≠ Empty`) → иначе `PortalEmpty`.
4. **Проверки по действию** (таблица ниже).
5. **Свободный штат** (для `SendObserver`/`SendRescuer`).
6. **Достаточно ресурса** (`power >= cost(action)`) → иначе `NotEnoughPower`.
7. → `None` (действие разрешено).

> **Почему ресурс проверяется последним.** Игроку важно знать сначала, структурно
> ли возможно действие, и лишь потом — хватает ли ресурса сегодня. Порядок
> формирует осмысленное сообщение.

#### Таблица проверок по действию (шаг 4)

|---|---|
| `ToggleQuestioned` | — |
| `Stabilize` | `surveyed` → иначе `NotSurveyed` |
| `Destabilize` | `surveyed` → иначе `NotSurveyed` |

#### Решение 3: порог закрытия для неразведанного портала

`Close` разрешён если: `hoursToCollapse <= closeHoursAtMost` **ИЛИ** (`surveyed &&
stability < closeStabilityBelow`). Для неразведанного портала работает только
временной порог — стабильность неизвестна и поле `stability` содержит `0`, что
было бы ложным разрешением. Проверяем `p.surveyed` перед использованием `p.stability`.

#### Решение 4: нельзя отозвать наблюдателя, пока разведка в процессе

`RecallObserver` возвращает `SurveyPending`, если `surveyPending == true`.
Причина: у Pyth-разведки два шага (request → callback); если наблюдатель уйдёт до
колбэка, результат некуда записать — callback попытается обновить поля портала,
которые уже неактуальны. Заодно это фиксирует, что результат разведки всегда
присваивается.

#### Решение 5: спасатель ходит вслепую; осторожная оценка риска — только ему

Спасателя (и эвакуацию) **больше не гейтит `NotSurveyed`**: в неразведанный портал
можно послать спасателя, не зная, что внутри. Это и есть риск, который смотритель
берёт на себя, когда время вышло раньше разведки. Проверка `creatures == 0 →
NoCreatures` осталась, но применяется **только при `creaturesKnown`**: пока число
неизвестно, пустота — часть ставки.

Риск разведанного портала считается точно (`RiskLib.portalRisk`). Для
**неразведанного** вводится осторожная оценка `RiskLib.cautiousPortalRisk` — риск по
**худшему углу** публичных диапазонов: `stability = stabilityLo` (наименее стабильно),
`energy = energyHi` (максимум энергии), `hoursToCollapse` как есть (всегда точно),
`lives = creaturesHi + наблюдатель_внутри + посылаемый_спасатель`. Если этот риск
`Critical`, `SendRescuer` возвращает `RiskTooHigh`.

> **Почему осторожная оценка касается ТОЛЬКО спасателя, а не наблюдателя.**
> Наблюдатель гейтится риском лишь у **разведанного** портала (§4.2, строка
> `SendObserver`): «послать наблюдателя — это и есть разведка», смотреть можно
> всегда. Если распространить осторожную оценку и на наблюдателя, опасный
> неразведанный портал станет **тупиком**: внутрь нельзя послать никого (и спасателя,
> и наблюдателя), а стабилизировать нельзя — стабилизация требует разведки, которой
> уже не будет. Портал окажется недостижим навсегда, и у игрока не останется ни
> одного хода. Оставляя наблюдателя без гейта, мы всегда держим открытым путь
> «разведать → узнать настоящие числа → стабилизировать».

#### Решение 6: слепое спасение, «один в темноте», выбывание спасателя

**Слепой заход (`SendRescuer` при `!creaturesKnown`).** Настоящее число существ
рождается в момент входа: бросок в `[creaturesLo, creaturesHi]`, `creaturesKnown =
true`, диапазон схлопывается в точку (`creaturesLo = creaturesHi = creatures`) — как
в `_survey`, чтобы в структуре не лежало два источника правды. Если выпал `0`,
спасатель **внутрь не входит** (`rescuerInside` остаётся `false`): портал пуст. Он
уходит на восстановление (см. ниже), выпускается событие `RescuerRecovering`.

**«В темноте одного упускаешь всегда» (`Evacuate` без разведки).** Разведанный портал
эвакуируется целиком (`saved = creatures`). Портал, в который вошли **вслепую**
(`surveyed == false`, даже если `creaturesKnown` уже `true` после слепого захода),
всегда оставляет одного: `saved = creatures − 1` при `creatures > 0`, иначе `0`.
Повторный слепой заход в остаток спасёт `n − 1 = 0`, то есть никого. Забрать
последнего можно **только разведав портал** (тогда `surveyed = true` и эвакуация
берёт всех). Это законный путь, а не дыра — **не «чинить»**.

**Выбывание спасателя.** Спасатель, вошедший в пустой портал вслепую, уходит на
`rescuerCooldownHours` игровых часов. `Game` держит ленту из `MAX_RESCUERS` ячеек
(`rescuerReadyAt0..3`): занятая ячейка хранит игровой час возвращения, `0` — ячейка
свободна. При пустом заходе занимается первая свободная ячейка, туда пишется
`текущий_час + rescuerCooldownHours`. В `TimeLib.catchUp` (после вычисления `hNow`)
каждая ячейка с `0 < readyAt <= hNow` обнуляется, `rescuersFree++` — это **сравнение**
с текущим часом, а не цикл по часам (ленивое время сохранено). `rescuersFree` никогда
не превышает `rescuersTotal`.

> **Почему лента — четыре скаляра, а не `uint32[MAX_RESCUERS]`.** Массив в Solidity
> **всегда начинает новый слот хранения**, и поле после него — тоже; массив раздул бы
> `Game` с двух слотов до трёх (измерено: 96 байт, `Player` 480). Четыре скаляра
> пакуются во второй слот рядом со `spawnCount`/`rngNonce` (8 + 16 = 24 из 32),
> оставляя `Game` **ровно два слота** (а `Player` — четырнадцать). Свободные
> функции `rescuerReadyAt` / `setRescuerReadyAt` в `PortalLabTypes` дают скалярам
> массивоподобный доступ по номеру (цепочка `if`, индекс вне диапазона —
> `revert`), чтобы логика читалась как цикл.

**Ограничение деплоя.** `rescuersTotal <= MAX_RESCUERS` (=4), иначе
`InvalidConfig("rescuersTotal")` — иначе ленты не хватит на всех восстанавливающихся.

### 4.3. Экономика действий

**Ресурс лаборатории (`power`).** Шкала 0..`POWER_MAX`, восстанавливается
`POWER_REGEN` за игровой час (та же формула времени). Каждое действие списывает
стоимость; не хватает — `NotEnoughPower`.

Стоимости (стартовый `DefaultConfig`, тюнятся):

| Действие | Стоимость |
|---|---|
| `ToggleQuestioned` | 0 |
| `Stabilize` | 5 |
| `Destabilize` | 5 |
| `SendObserver` | 10 |
| `RecallObserver` | 5 |
| `SendRescuer` | 20 |
| `RecallRescuer` | 10 |
| `Evacuate` | 10 |
| `Close` | 25 |

**Штат.** `OBSERVERS_TOTAL` (3) наблюдателей и `RESCUERS_TOTAL` (2) спасателей
(`rescuersTotal <= MAX_RESCUERS`, §4.2 Решение 6). Человек занят, пока внутри, и
освобождается при отзыве, эвакуации или закрытии. Погибает вместе с порталом при
схлопывании — и **не возвращается в штат**.

Отдельный случай — спасатель, вошедший вслепую в **пустой** портал (§4.2 Решение 6):
он не гибнет, но выбывает на `rescuerCooldownHours` игровых часов на восстановление,
после чего возвращается в штат сам (по формуле в `TimeLib.catchUp`, не по циклу).

> **Стартовый вариант, подлежит проверке.** Если безвозвратная потеря окажется
> слишком жёсткой, правило меняется на восстановление штата через
> `CREW_RESPAWN_HOURS` игровых часов. Решается после первых прогонов.

> Это превращает булевы флаги `observerSent`/`rescuerSent` оффчейн-версии в
> настоящий дефицит: кого вытаскивать, а кого бросить.

**Порог нестабильности.** `Close` разрешён только если `stability < closeStabilityBelow`
(после разведки) или `hoursToCollapse <= closeHoursAtMost`. Свежий устойчивый портал
закрыть нельзя — нечего схлопывать. Чтобы закрыть раньше, применяется `Destabilize`:
ускоряет падение стабильности, но повышает риск.

> **Зачем всё это.** В оффчейн-версии действия бесплатны и неограниченны, поэтому
> оптимальная стратегия — закрывать каждый портал в момент появления. Ноль риска,
> бесконечная жизнь, игры нет. Три ограничителя выше убирают эту стратегию и делают
> осмысленными все остальные действия.

### 4.4. HP — потери и восстановление

Старт `HP_START` (напр. 50), потолок `HP_MAX` (напр. 100) — эвакуация может поднять
HP выше стартового, но не выше потолка. **Таблица — плейсхолдер, тюнится тестами-сценариями.**

| Событие | Изменение HP |
|---|---|
| Схлопывание портала с живыми внутри | −(`hpCollapseBase` + `hpCollapsePerDeath` × погибших) |
| **Закрытие портала с живыми внутри** | **−(`hpCollapsePerDeath` × погибших)** (без base!) |
| **Закрытие пустого портала** | **0** |
| Схлопывание пустого портала | −`hpEmptyCollapse` |
| Переполнение: открыто 12 порталов, за каждый лишний час | −`hpOverflowPerHour` / час |
| **Спасено существо (эвакуация)** | **+`healPerCreature`** |

`hp <= 0` → партия окончена. Счёт = `hoursElapsed` на момент смерти.

> **Штраф — только по факту гибели.** Разумный риск при живой разведке не
> наказывается. Закрытие пустого портала — обычная работа смотрителя и HP не
> стоит; схлопывание пустого стоит `hpEmptyCollapse`, потому что это провал.

**Погибшие при закрытии.** `deathsCreatures = creaturesKnown ? creatures : creaturesHi`.
`deaths = deathsCreatures + наблюдатель_внутри + спасатель_внутри`. Для портала с
неизвестным числом существ берётся **верхняя граница** `creaturesHi` — игрок видит
наихудший сценарий заранее. Поле `creatures` не читается, пока `creaturesKnown=false`.
Погибший экипаж **не возвращается в штат** (§4.3). Слот обнуляется до `Empty`, `openPortals−−`.

> **Почему закрытие и схлопывание с живыми стоят по-разному — и почему это важно
> не выравнивать.** Схлопывание — несчастный случай: смотритель не успел. Штраф =
> `hpCollapseBase` (за провал) + `hpCollapsePerDeath × midpoint` (за погибших по
> середине диапазона — игрок не знал точное число). Закрытие — сознательное
> решение: смотритель выбрал закрыть. Штраф = `hpCollapsePerDeath × creaturesHi`
> (за погибших по верхней границе — плати за худший сценарий), без базового штрафа
> (ты не проворонил, ты выбрал). Две разные ситуации → две разные формулы.
> Попытка «выровнять» их ломает экономику: одинаковая цена убирает стимул
> предотвращать схлопывания (проще закрыть и не заморачиваться).

**Обязательное условие баланса.** Портал за свою жизнь должен в среднем уносить
больше HP, чем приносит. Иначе порталы становятся источником HP, а игра —
бесконечной, что противоречит §4.6.

Держится тремя рычагами: хил меньше штрафа за гибель; спасение стоит ресурса и
штата, поэтому спасти всех физически нельзя; сложность растёт быстрее хила.

**Проверяется тестом, а не на глаз:** сценарий «идеальная игра» должен
заканчиваться смертью. Если не заканчивается — баланс сломан, и это видно сразу.

### 4.5. Типы порталов

Тип — `uint8`, его параметры лежат отдельной таблицей, чтобы балансировать не
трогая логику. Числа — плейсхолдеры.

| Тип | Суть | Механика |
|---|---|---|
| **Вспышка** | живёт часы, требует немедленных решений | `hoursMin=5, hoursMax=10`, ускоренная деградация, всегда населён (2–3 существа); разведка часто не окупается, но закрыть вслепую тоже дорого |
| **Долгожитель** | живёт долго, копит проблему | большой `hours`, замедленная деградация, больше существ внутри |
| **Глухой** | информация неполна всегда | разведка не даёт точного значения, только сужает диапазон; единственный тип, где закрытие вслепую — нормальная тактика |
| **Резонансный** | полностью управляем, но хрупок | `stabilize` и `destabilize` действуют вдвое сильнее; деградация тоже ускорена |
| **Энергетический** | кормит лабораторию | пока открыт, **прибавляет** `power` вместо расхода |

> **Энергетический — ключевой.** Это единственный тип, создающий причину **не
> закрывать** портал: держать у себя опасную штуку ради топлива или закрыть и
> остаться без ресурса. Он прямо работает против вырожденной стратегии «закрой всё».
>
> **Каскад отклонён.** Идея «схлопывание бьёт по соседям» рассмотрена и отброшена:
> список отсортирован по близости к схлопыванию, поэтому каскад вырождается в
> конвейер и решений игроку не добавляет.

### 4.6. Нарастание сложности

Сложность растёт **безгранично** — вечное выживание невозможно, иначе лидерборд
бессмыслен. Растут: скорость деградации и **давление спавнов**. Конкретная кривая
тюнится; принцип обязателен и проверяется тестом из §4.4.

**Давление спавнов — замкнутая формула.** Партия копит «давление»
(`Game.spawnDebt`, в тысячных долях портала). Каждый прожитый игровой час
добавляет `basePressurePerHour + pressureRampPerHour × h`, где `h` — номер
игрового часа: чем дольше идёт партия, тем быстрее копится давление (это и есть
нарастание сложности). За отрезок часов `[a, b)` прирост считается **суммой
арифметической прогрессии одной формулой**, без цикла по часам:

```
Δpressure = base × (b − a) + ramp × ((a + b − 1) × (b − a)) / 2
```

`(a + b − 1) × (b − a)` всегда чётно (это удвоенная сумма подряд идущих чисел),
поэтому деление на 2 точно. Давление насыщается на `SPAWN_DEBT_MAX` — очень
долгая пауза не переполняет `uint32`. Когда накоплено `spawnCostUnits`, рождается
портал (см. §7). Цикл по часам запрещён так же, как в старении (§5.2): формулу
умеет повторить фронт, а цикл — нет.

### 4.7. Рекомендации и сортировка

`recommendAction` и `comparePortals` — чистая презентация, считаются **на клиенте**
из ончейн-состояния. В контракте не нужны.

### 4.8. Почему партия обязана закончиться

Без давления, растущего по формуле (§4.6), партия может длиться бесконечно: если
`pressureRampPerHour == 0`, игрок в пределе закрывает порталы ровно с той же
скоростью, с которой они появляются, и больше никогда не умирает. **Это нарушает
баланс.** Решение — рамп, и тогда граница становится аналитически доказуемой.

**Вывод границы** (максимальный случай — все 12 слотов заняты Энергетическими
порталами, разведка бесплатна, существа не мешают):

Пусть `H` — критический час, когда спавны впервые превышают удаления.

- Максимальный доход ресурса в час:
  ```
  maxIncome = POWER_REGEN_PER_HOUR + 12 × max(powerYieldPerHour)
  ```
- Стоимость удаления одного портала (закрытие минус бонус закрытия):
  ```
  netPerClose = spawnCostUnits − closePressureBonus
  ```
- Максимум давления, которое можно удалить в час (потратив весь доход на закрытие):
  ```
  maxRemovalPerHour = (maxIncome / costClose) × netPerClose
  ```
- Спавн-давление растёт как:
  ```
  spawnRate(h) = basePressurePerHour + pressureRampPerHour × h
  ```
- Критический час `H` — наименьший час, где `spawnRate(H) > maxRemovalPerHour`.

**На текущих параметрах** (DefaultConfig):
- `maxIncome` = 5 + 12 × 4 = 53 ед./час;
- `netPerClose` = 10_000 − 2_500 = 7_500 ед./портал;
- `maxRemovalPerHour` ≈ (53 / 25) × 7_500 ≈ 15_900 ед./час;
- `spawnRate(0)` = 1_000; `spawnRate(h) = 1_000 + 1 × h`;
- `H` ≈ 14_900 часов (≈ 223 тыс. реальных секунд ≈ 62 часа).

**Это — верхняя граница в лучшем случае.** Реальный игрок:
- не имеет бесплатную разведку;
- не может закрыть ВСЕ портальные-энергетические в любой момент (нужна стабильность,
  дальность коллапса);
- теряет HP на спасение существ и схлопывания;
- имеет конечный штат.

Поэтому `H' < H` всегда. **Гарантия конечности зависит критически от
`pressureRampPerHour > 0`.** При балансировке (Веха 7) нельзя обнулять рамп:
это разом превращает выживалку в бесконечную.

## 5. Время — ленивое, вычисляется формулой

### 5.1. Принцип

Контракт не исполняется между транзакциями: в блокчейне нет таймера и фонового
процесса. Поэтому мир стареет **задним числом**: при любой транзакции контракт
смотрит на `block.timestamp`, вычисляет прошедшие игровые часы, приводит состояние к
текущему моменту и только потом применяет действие игрока.

Фронт при этом рисует старение непрерывно: он читает снимок, применяет ту же
формулу и показывает актуальный мир **без единой транзакции**. Для игрока ленивое
время неотличимо от непрерывного.

### 5.2. Формула старения

Для каждого живого портала, от снимка на `snapshotAt`, при `h` прошедших игровых
часах:

```
stability(h)       = max(0, stability₀ − degradeRate(type) × h)
hoursToCollapse(h) = max(0, hours₀ − h)
```

Момент схлопывания известен из снимка сразу:
`collapseAt = snapshotAt + hours₀ × SEC_PER_HOUR`.

Ресурс лаборатории: `power(h) = min(POWER_MAX, power₀ + POWER_REGEN × h + вклад
энергетических порталов)`.

**Никаких циклов по часам.** Стоимость догона — O(числа порталов), то есть не больше
двенадцати шагов, независимо от длины паузы. Это **требование**, а не пожелание:
цикл по часам не влезает в блок уже при пятиминутном отсутствии и, главное, его не
может повторить фронт, а формулу — может (§2.1).

**Всё считается в домене игровых часов.** Игровой час отметки времени `t` —
`h(t) = (t − startedAt) / SEC_PER_HOUR` (отбрасывание). **Все интервалы берутся как
разности `h(...)`**, а не как разности отметок, делённые по отдельности: иначе
отбрасывание на каждом отрезке накопит расхождение с общим числом часов. Час
схлопывания портала — `h(snapshotAt) + hoursToCollapse`; это ровно `h(collapseAt)`
(так как `hoursToCollapse` целое), поэтому старение и обнаружение схлопывания
согласованы, и пересъёмка уцелевшего портала на `nowTs` **сохраняет** его момент
схлопывания (нет дрейфа, `preview` всегда равен `sync`).

Реализация — `TimeLib.catchUp` (тикет 1.6): чистая функция, возвращающая новое
состояние и список случившихся схлопываний; события эмитит контракт.

### 5.3. Приведение состояния (`catchUp`) и момент смерти

**Главное свойство: мир не зависит от того, КОГДА кто-либо вызывает.** Час каждого
события — схлопывания и рождения — есть функция снимка и времени. Поэтому одно
приведение к `c` оставляет ровно то же состояние (игра и все двенадцать порталов),
что приведение к `b`, а затем к `c`, для любого `b` между ними; два вызова в один
момент равны одному. Именно это делает безвредным то, что `sync` бесплатен и открыт
любому: посторонний вызов — лишь наблюдение. (Раньше портал рождался в час вызова,
и один чужой `sync` в выбранный час мог убить партию — `RepeatedFreeSync.t.sol`.)

Обозначения: окно приведения — игровые часы от `H0 = h(lastTickAt)` до `hEnd`;
`hEnd = h(nowTs)` или, если следующая эпоха не закреплена словом, последний час
закреплённой эпохи (§6). `debt0 = spawnDebt`. Давление, доступное к часу `h`:
`A(h) = debt0 + spawnPressure(H0, h)` (§4.6).

Алгоритм `TimeLib.catchUp`:

1. **Партия не начата или `finished`** (или `nowTs < startedAt`) — вернуть без
   изменений. Часы, отстающие от `lastTickAt` (например, медленные часы браузера),
   считаются «время не прошло»: `nowTs` поджимается к `lastTickAt`, результат
   равен вызову в `lastTickAt`.
2. Для каждого занятого слота вычислить час схлопывания
   `h(snapshotAt) + hoursToCollapse`; посчитать число открытых порталов и сумму их
   `powerYieldPerHour`.
3. **Рождения.** k-е рождение окна (k = 1, 2, …) происходит в наименьший час `h`,
   не раньше часа предыдущего обработанного события, такой что
   `A(h) >= k × spawnCostUnits` **и** в этот час есть свободный слот. Если
   лаборатория полна, созревшее рождение ждёт и происходит в час первого
   схлопывания, освободившего слот. Ограничения на число рождений за вызов нет.
   Час созревания ищется без перебора часов: оценка `ceil(недостача / r)`, где `r` —
   давление первого часа поиска (каждый следующий час даёт не меньше), с проверкой
   соседнего часа, а в остальных случаях — двоичный поиск с пределом 64 итерации.
4. **Один хронологический проход по событиям:** схлопывания (и хранимых порталов, и
   рождённых в этом окне) и рождения. В одинаковый час — сначала схлопывания по
   возрастанию слота, затем рождения. Между событиями, на отрезке длиной `Δ`:
   - **ресурс:** `power += (POWER_REGEN + сумма powerYieldPerHour открытых
     порталов) × Δ`, потолок `POWER_MAX`;
   - **переполнение:** если открыто ровно 12 порталов,
     `hp -= HP_OVERFLOW × Δ`. Если HP дошёл бы до нуля внутри отрезка — смерть в
     часе `h(начала отрезка) + ceil(hp / HP_OVERFLOW)`, дальше не считать.

   **Схлопывание:** `deaths = creaturesKnown ? creatures : (creaturesLo +
   creaturesHi) / 2`, плюс наблюдатель и спасатель внутри; `hpLost = deaths > 0 ?
   HP_COLLAPSE_BASE + HP_COLLAPSE_PER_DEATH × deaths : HP_EMPTY_COLLAPSE`; экипаж
   внутри **погибает** и в штат не возвращается; слот обнуляется; событие с часом
   схлопывания. Если HP дошёл до нуля — смерть в этот час, дальше не считать.

   **Рождение** в час `b`: см. §7 — первый свободный слот, `spawnedAtHour = b`,
   `snapshotAt = startedAt + b × SEC_PER_HOUR`. С часа `b` это обычный открытый
   портал: даёт энергию, считается в двенадцать, может схлопнуться в том же окне.
5. **Предохранитель.** Цикл событий ограничен константой `MAX_CATCHUP_EVENTS = 64`.
   Если она исчерпана, приведение останавливается в часе последнего обработанного
   события и сообщает об этом так же, как о закреплённой границе (`cappedShort =
   true`, мир помечен этим часом): `preview` и `sync` совпадают, следующий вызов
   продолжает. В настоящей игре это недостижимо: каждое схлопывание стоит HP,
   схлопывание неразведанного новорождённого — не меньше `HP_COLLAPSE_BASE +
   HP_COLLAPSE_PER_DEATH` (30), а HP не превышает `HP_MAX`.
6. **За закреплённой границей** (мир не дошёл до `h(nowTs)`) — детерминированная
   смерть §5.5, без порталов в хвосте.
7. **Если смерть наступила:** `finished = true`, `diedAtHour = hoursElapsed = час
   смерти`; часы партии останавливаются на смерти: `lastTickAt = startedAt + час
   смерти × SEC_PER_HOUR` (а не момент вызова — иначе мир зависел бы от того, кто и
   когда посмотрел). Порталы **замораживаются на моменте смерти**: уцелевшие
   состарены к часу смерти (при смерти за границей — к границе) и помечены этим
   часом. `spawnDebt` — давление, доступное к этому часу, за вычетом потраченного
   на рождения.
8. **Иначе:** `hoursElapsed = hEnd`, `lastTickAt = nowTs` (или отметка часа
   остановки, если мир упёрся в границу либо в предохранитель); каждый уцелевший
   портал — и хранимый, и рождённый в окне — состарить (`stability -=
   degradePerHour × e` для разведанного, пол 0; диапазоны неразведанного шире на
   `rangeWidenPerHour × e`; `hoursToCollapse -= e`, где `e = hEnd − h(snapshotAt)`)
   и поставить `snapshotAt` на ту же отметку. `spawnDebt = min(SPAWN_DEBT_MAX,
   A(hEnd) − рождений × spawnCostUnits)`. Спасатели, чей срок восстановления
   наступил к часу отметки, возвращаются в штат.

Старение составное: два шага `e1` и `e2` дают то же, что один шаг `e1 + e2`; это и
держит разбиение приведения равным одному приведению.

Счёт фиксируется по моменту смерти, а **не** по моменту, когда игрок вернулся.
Отсутствие не даёт ни одного лишнего очка.

> **Схлопывание пустого стоит `HP_EMPTY_COLLAPSE`** — в отличие от **закрытия**
> пустого портала, которое бесплатно (§4.4): закрытие — работа смотрителя, а
> схлопывание — его провал.

> **`sync(player)` открыт для любого вызывающего.** Приведение детерминированно и
> навредить не может, а внешний «будильник» при желании подтолкнёт мир вперёд, не
> меняя контракт. `preview(player)` — то же приведение в памяти, без записи
> (для фронта и как проверка, что чтение и запись совпадают). `act` приводит
> состояние **первым делом**, до проверки действия.

### 5.4. Короткая пауза

Обычная пауза считается активной игрой: порталы стареют по §5.2, давление копится
формулой (§4.6), и каждый портал рождается **в час созревания своего давления**
(§5.3, §7), а не в час, когда кто-то вызвал приведение. Ограничения на число
рождений за вызов нет. Момент появления детерминирован; случайно только содержимое
портала (слово Pyth эпохи часа рождения, §6). Давление, которому не хватило
свободного слота, не теряется: рождение ждёт первого освободившегося слота.

### 5.5. Длинная пауза — детерминированное переполнение

Отдельной ветки «по таймеру бездействия» нет: длинная пауза считается **тем же
проходом по событиям**, что и короткая (§5.3). Пока мир идёт по закреплённым
эпохам, порталы рождаются в часы созревания, новорождённые схлопываются, HP
тратится, переполнение (12 открытых) включается само — заброшенная лаборатория
умирает как следствие правил, а не по отдельной формуле. Число событий одного
вызова ограничено предохранителем (§5.3, п. 5), не длиной паузы.

> **Следствие для баланса.** Брошенная лаборатория теперь умирает заметно раньше,
> чем при прежней аналитической формуле: например, пустая лаборатория со 100 HP при
> словах тестового стенда гибнет к 57-му часу (раньше — 134-й), потому что порталы
> действительно рождаются за время отсутствия и схлопываются.

**За закреплённой границей** (следующая эпоха не закреплена словом, мир дошёл только
до `hEnd < h(nowTs)`) рождений нет — для них нужно слово. Но переполнение слова не
требует, поэтому режим «заброшенной лаборатории» сохраняется для хвоста
`[hEnd, h(nowTs)]`, от состояния на `hEnd` (открыто, остаток давления, HP):

1. **Час заполнения `hFill`** — наименьший час, в который остатка давления плюс
   `spawnPressure(hEnd, hFill)` хватило бы на `(MAX_OPEN_PORTALS − открыто на
   hEnd)` порталов. Ищется без перебора часов (оценка и двоичный поиск, предел 64
   итерации).
2. Если `hFill + ceil(hp / hpOverflowPerHour) <= h(nowTs)`, партия кончается:
   `diedAtHour = hFill + ceil(hp / hpOverflowPerHour)`. **Порталов в хвосте не
   создаётся.** Мир замораживается на `hEnd`.

Как и прежде, лаборатория, уже полная на `hEnd`, этим правилом не рассматривается
(правило заполняет лабораторию, а не осушает полную), и при `hpOverflowPerHour = 0`
оно не действует. Если граница не мешала (мир дошёл до `h(nowTs)`), отдельного шага
нет: переполнение возникает из п. 4 §5.3.

> **Почему так.** Запросить у Pyth сотню бросков за пропущенный час нельзя ни по
> газу, ни по деньгам. Но главная причина другая: случайное фронт предсказать не
> может, и после долгой паузы экран врал бы до первой транзакции — а это нарушает
> инвариант §2.1. Момент заполнения детерминирован (давление — чистая формула
> времени), поэтому фронт считает `hFill` и час смерти сам, без единой транзакции.
> Фикция сходится: за лабораторией никто не следил, она переполнилась.

### 5.6. Темп

`SEC_PER_HOUR` — **15 секунд на игровой час** на старте. Значение выбрано как
компромисс и **подтверждён замерами Вехи 0 (§14.1); окончательно — после Вехи 4**.

Ограничение снизу: игровой час должен быть заметно длиннее, чем подтверждение
транзакции плюс колбэк Pyth. Иначе разведка не успевает вернуться до схлопывания
портала.

Ограничение сверху: темп × ожидаемая выживаемость = длина сессии. Цель — сессия на
20–40 минут и достаточный разброс в счёте, чтобы различать игроков. Темп и кривая
сложности тюнятся **совместно**, это фактически один параметр.

Фронт **читает `SEC_PER_HOUR` из контракта**, а не хардкодит.

### 6.2. Что берёт случайность

Только два потребителя, и оба **при активной игре**:

1. **Разведка** — тайминг-чувствительна (иначе игрок подгадывает низкий риск).
2. **Спавны порталов** при коротких паузах.

Длинная пауза случайности не требует (§5.5).

### 6.3. Двухфазность

Запрос энтропии асинхронный: контракт делает `request` с комиссией, значение
приходит в fulfillment-колбэке отдельной транзакцией. Следствия:

- **разведка двухфазна**: `sendObserver` → `surveyPending = true` → колбэк
  записывает точные значения внутри текущего диапазона и снимает флаг;
- **спавн двухфазен** тем же образом.

Одного 256-битного значения хватает на несколько бросков — нарезается на части,
второй запрос за транзакцию не нужен.

### 6.4. Безопасность и liveness

- Колбэк может звать только контракт Pyth; защита от повторного входа.
- **Liveness — закрыто в §6.7:** застрявшее действие отменяется через
  `cancelDeferred` по таймауту реального времени. Перезапроса нет.
- Комиссию Pyth платит session-key игрока.

### 6.5. Тестирование

`forge test --fork-url` **не применяется**: из рабочего окружения RPC Monad
недоступен. Интеграция тестируется моками Entropy в Foundry, включая сценарий «колбэк
не пришёл». Первая встреча с живым Pyth — на деплое; закладывать запас.

### 6.6. Заглушка-рандом Вехи 1 (`RandomStub`) и её предсказуемость (Решение 1)

Настоящий Pyth появляется только на Вехе 4. До него разведка (и позже спавны)
питаются **заглушкой** `RandomStub`: `draw(player, nonce, salt) =
keccak256(player, nonce, salt)`, отображённой на диапазон через `inRange`. Соль
различает параметры внутри одного броска (энергия/стабильность/существа не
коррелируют), `nonce` — это `Game.rngNonce`, растущий с каждой разведкой.

> **⚠️ Заглушка полностью предсказуема — и это известная, записанная дыра, а не
> недосмотр.** Результат есть чистый `keccak` от адреса игрока и счётчика, поэтому
> **любой, включая игрока, может вычислить исход следующего броска ОФФЧЕЙН до
> отправки транзакции.** Прямое следствие: игрок разведывает **только при
> выгодном броске** (низкий риск), а невыгодный откладывает — то самое
> предвидение, ради устранения которого выбран Pyth (§13, журнал решений). Снимается
> это **только** настоящим Pyth Entropy, чьё значение неизвестно до
> fulfillment-колбэка (§6.3).

> **Заглушка НЕ должна зависеть от свойств блока** (`block.timestamp`,
> `block.prevrandao`, `blockhash`). Она обязана быть чистой функцией явных входов,
> иначе результат перестанет быть воспроизводимым в тестах и — главное — во
> фронте, который по инварианту §2.1 обязан локально повторить вычисление
> контракта.

> **В сеть с заглушкой выходить нельзя** — см. открытый вопрос §11.9.

### 6.7. Веха 4 — итог: что построено

- **Двухфазные действия.** Разведка и слепой заход спасателя фиксируются в
  транзакции игрока (сила списана, экипаж внутри, портал помечен), а результат
  рождается в колбэке `receiveWord`. Отложенное действие у игрока одно; пока оно
  висит, любое другое отказывает с `ActionPending`. Запись отложенного —
  `Pending` (один слот, 26 байт из 32).
- **Эпохи и заглядывание на 36 часов.** Одно слово Pyth закрепляется на эпоху в
  `epochHours` = 36 игровых часов (9 реальных минут; было 12 — решение владельца:
  реже платить за энтропию); сиды спавнов выводятся из закреплённого слова.
  Первый край эпохи — час 35. Содержимое новорождённого берётся из
  `epochSeed(слово, b / epochHours)`, поэтому при смене `epochHours` те же слово и
  час рождения попадают в другую эпоху и дают другие типы, сроки и часы смерти:
  правило то же, кости другие.
  Игрок может предсказать мир не дальше края закреплённых эпох. Действие, которое
  пересекает край, откладывается целиком (`deferredWorld`): мир стареет только в
  колбэке, по старому слову для закреплённых эпох и по новому дальше.
- **Сменный источник случайности.** Игра говорит с `IRandomSource`; Pyth Entropy V2
  (`PythEntropySource`) — один из вариантов, адрес неизменен после деплоя. Тесты
  идут через `DeterministicSource`.
- **Оплаченный sync.** `sync(player)` бесплатен и стареет мир до края эпох; с
  `msg.value > 0` он на краю запрашивает слово и проводит мир через границу
  (`syncOnly`). Комиссию платит вызывающий, не игрок; сдача возвращается ему.
- **Таймаут и отмена (Тикет 4.7), два порога.** Если слово не пришло, застрявшее
  отложенное действие можно отменить `cancelDeferred(player)`:
  - **сам игрок** — через `requestTimeoutHours` (1 игровой час = 15 с);
  - **кто угодно другой** — только через `outsiderTimeoutHours` (40 игровых
    часов = 10 реальных минут). Порог постороннего строго не меньше порога игрока
    (конструктор отвергает `outsiderTimeoutHours` = 0 и меньше
    `requestTimeoutHours`).
  - *Почему два.* Отмена стоит игроку комиссии Pyth (она уже у провайдера). При
    одном коротком пороге любой посторонний мог через 15 с после фиксации отменить
    чужое действие и сжечь комиссию, если Pyth просто медленнее этих 15 с. Теперь
    свою застрявшую заявку игрок снимает быстро, а чужая получает 10 минут на
    доставку слова; посторонний нужен лишь как страховка на случай, когда сам
    игрок исчез.
  - Граница строгая в обоих случаях: ровно на пороге отказ
    `RequestNotTimedOut(availableAt + 1)`, на секунду позже — можно.
  - Время меряется **реальными часами** (`block.timestamp` против `committedAt`
    в `Pending`), а не игровыми: именно пересекающее эпоху действие застревает
    потому, что игровые часы стоят, и игровой таймаут не сработал бы никогда.
  - Экипаж возвращается **живым**: портал цел, наблюдатель выходит обратно (при
    обвале он, напротив, погибает вместе с порталом); спасатель до раскрытия
    внутрь не заходил.
  - Сила возвращается только там, где списывалась при фиксации: половина,
    округление в пользу игрока (10 → 5, 5 → 3). У пересекающего эпоху действия
    сила списывается лишь на раскрытии, возвращать нечего.
  - В событии `DeferredActionCancelled` причина `Refusal.RandomnessTimeout` —
    отличать сбой провайдера от игровых отказов по логам. Текст для игрока — дело
    фронта.
  - Слово, пришедшее после отмены, отваливается как `UnknownRequest`.
  - Перезапроса нет, только отмена.

> **ЯВНО И БЕЗ СГЛАЖИВАНИЯ: сбой оракула стоит игроку комиссии, и вернуть её
> контракт не может — она уже у провайдера.** Таймаут возвращает партию в
> рабочее состояние, но не деньги. Комиссия не возвращается никогда.

## 7. Спавны и старт партии

**Момент появления детерминирован, случайно только содержимое.** Партия копит
давление формулой §4.6; набралось `spawnCostUnits` — рождается портал, давление
тратится. Так фронт может предсказать момент и заранее показать, что скоро станет
хуже; длинная пауза считается той же формулой без отдельной ветки (§5.5); а Pyth
в Вехе 4 понадобится только на **содержимое** — одного 256-битного броска хватит
на несколько порталов.

- **Старт:** `startGame` кладёт в `spawnDebt` давление трёх порталов
  (`3 × spawnCostUnits`). Оно созрело уже в час 0, поэтому стартовая тройка
  рождается **в час 0**, как только эпоха 0 закреплена словом (платный `startGame`
  или первый платный `sync`/`act`), — в каком бы часу ни пришло слово.
- **Спавн — в час созревания, а не в час вызова:** k-й портал окна приведения
  рождается в наименьший час `h` (не раньше предыдущего события), когда
  `debt0 + spawnPressure(H0, h) >= k × spawnCostUnits` и есть свободный слот; при
  полной лаборатории — в час схлопывания, освободившего слот (§5.3). Портал
  занимает первый свободный слот; ограничения на число рождений за вызов нет.
  После приведения `spawnDebt` — доступное к концу окна давление за вычетом
  `spawnCostUnits` на каждое рождение (с насыщением `SPAWN_DEBT_MAX`).
- **Закрытие добавляет давление:** действие `Close` (не схлопывание) сразу
  прибавляет `closePressureBonus` к `spawnDebt` — «закрыл один, открылось
  несколько». Схлопывание давления не добавляет.
- **Содержимое портала — жребием** (в Вехе 1 через заглушку `RandomStub`,
  `rngNonce` растёт перед каждым порталом): тип равновероятно из пяти;
  `hoursToCollapse` — точное значение в диапазоне `hoursMin..hoursMax` типа
  (время публично всегда, §3.1); `nameIndex = бросок % NAME_POOL_SIZE`.
- **Энергия, стабильность и число существ НЕ бросаются при спавне** — портал
  рождается неразведанным (`surveyed=false`), с диапазонами типа как есть; точные
  значения рождаются при разведке (§6).
- `spawnedAtHour` = час рождения `b`; `snapshotAt = startedAt + b ×
  SEC_PER_HOUR` (дальше, как у любого уцелевшего, пересъёмка при каждом
  приведении); `id = ++spawnCount`; `rngNonce` растёт на единицу. Тип,
  `hoursToCollapse` и `nameIndex` берутся из сида эпохи часа рождения:
  `epochSeed(слово эпохи, b / epochHours)` (§6).
- **Имена на цепочке не хранятся** — только номер (`nameIndex`). Строка в storage
  стоит газа за каждую букву, а пользы контракту от неё нет; сами названия живут
  во фронте (пул на `NAME_POOL_SIZE` имён, перенести `SPAWN_NAMES` из
  оффчейн-версии).

## 8. Лидерборд и фиксация счёта

- **Один режим** (casual). Challenge с общим сидом невозможен: Pyth ⇒ недетерминизм.
- Хранится личный рекорд по адресу (`bestHours`) плюс событие на каждую фиксацию.
- **Фиксация:**
  - основной путь — игрок шлёт `settle`: контракт проверяет, что партия окончена,
    вычисляет момент смерти (§5.3), обновляет рекорд, эмитит событие;
  - оптимизация — если игрока добило его собственное действие, рекорд пишется инлайн
    в той же транзакции.
- **Старт новой партии при живой старой = слив предыдущей.** Иначе игрок бросает
  проигранный забег и переигрывает бесплатно.
- Доверия к серверу нет — счёт есть чистое ончейн-состояние.

## 9. Storage против событий

- **В storage** — только живое: активные порталы (≤12), HP, ресурс, штат,
  таймстемпы, счётчики, рекорды.
- **В события** — вся история: действия, схлопывания, спавны, отказы, журнал
  (аналоги `HistoryEntry`/`LogEntry`). Не хранятся в storage, реконструируются с
  фронта.
- События несут **игровое время наступления**, а не только время записи: при ленивом
  времени схлопывание попадает в блок позже, чем случилось.

## 10. Действия, газ, кошелёк, фронт

- **Каждое действие — транзакция.** Чтобы игра была играбельной в реальном времени,
  используется **session-key**: на старте партии игрок подключает кошелёк, один раз
  авторизует и финансирует burner-ключ, дальше действия шлются без попапа на клик.
- **Скоуп session-key (открытый вопрос, §11):** ключ должен уметь звать только
  игровые действия и держать малый баланс — утечка не должна стоить кошелька.
  Предпочтительна простая схема `mapping(burner => owner)` в контракте, а не
  ERC-4337: она решает задачу и не раздувает проект.
- Игрок платит свой тестнет-газ и комиссии Pyth (MON из крана — шаг онбординга).
- **Фронт:** React-UI из `../portal-lab/src/ui/*` переиспользуется как презентационный слой. Слой
  состояния (`appReducer`) заменяется на чтение ончейн-состояния, локальную проекцию
  времени и отправку действий.
- **Фронт обязан использовать TS-зеркало арифметики (§4.1)** и читать immutable-
  параметры из контракта. Любое расхождение видно игроку как «кнопка доступна, а
  контракт отказал».
- Дисконнект не обрабатывается специально: время идёт по цепочке независимо от
  вкладки.

## 11. Открытые инженерные вопросы

Закрыты в этой версии: ограничение газа догона (§5.2–5.5), порядок сборки (§12),
перенос арифметики (§4.1), вырожденная стратегия «закрой всё» (§4.3), конец партии
при бездействии (§5.3).

Остались:

1. **Liveness Pyth-колбэка** (§6.4). Таймаут и повтор для зависшей разведки.
2. **Скоуп и безопасность session-key** (§10).
3. **Async-состояния в UX**: как рисуем «разведка в процессе», чтобы игрок понимал
   задержку и не считал это зависанием.
4. **Старт партии** (§7): фиксированный дебют против случайного.
5. **Баланс**: таблица HP, стоимости действий, параметры типов, кривая сложности,
   значение `HEAL_PER_CREATURE`. Тюнинг после Вехи 0 и Вехи 6.
6. **Темп `SEC_PER_HOUR`** (§5.6): замер Вехи 0 выполнен (§14.1), `15` подтверждён;
   открытым остаётся только колбэк Pyth (Веха 4).
7. **Ленивое время и флаг `finished`.** Партия может быть мертва по формуле
   (§5.3), пока `finished` ещё `false`: флаг никто не пересчитал. Поэтому
   `startGame` и `settle` обязаны сначала выполнить догон времени и только
   потом решать, жива ли партия, — иначе погибшая партия засчитается как
   брошенная. Решается в тикете 1.6.
8. **Новая партия поверх мёртвой, но не зафиксированной.** Если игрок погиб и
   не отправил `settle`, `startGame` затрёт результат. Решается на Вехе 3
   вместе с лидербордом.
9. **В сеть с заглушкой-рандомом (`RandomStub`, §6.6) выходить нельзя.**
   Псевдослучайность Вехи 1 предсказуема оффчейн: игрок вычислит исход разведки
   до отправки и разведает только при выгодном броске. Деплой любой сетевой сборки
   обязан идти уже с настоящим Pyth Entropy (Веха 4); заглушка — только для
   локальных тестов.

## 12. Вехи

Порядок изменён: реальность сети и первая картинка в браузере подняты вперёд.
Причина — из рабочего окружения нет доступа к RPC, поэтому всё до деплоя
проверяется только локальными тестами, и чем позже первый деплой, тем дороже
сюрпризы.

**Веха 0. Разведка боем — выполнена (результаты в §14).** Контракт-счётчик на
двадцать строк, деплой на тестнет через Remix, десяток нажатий. Замеряем: газ за
транзакцию, задержку подтверждения и её разброс, поведение при быстрых транзакциях
подряд, хватает ли крана. **Главный вопрос: выдерживает ли сеть темп 15 секунд на
игровой час.** Если нет — меняем константу сейчас, пока это правка строки в SPEC, а
не переделка игры.

**Веха 1. Ядро домена на Solidity** с заглушкой-рандомом: структуры, матрица
действий и отказов, экономика (§4.3), типы порталов, старение формулой, HP,
схлопывания, вычисление момента смерти. Foundry-тесты трёх видов (§4.1) плюс
сценарий «идеальная игра» (§4.4).

**Веха 2. Тонкий срез до экрана.** Минимальный фронт на трёх действиях, без
лидерборда, без Pyth, без session-keys, обычный кошелёк с попапом на клик. Деплой на
тестнет. Цель — увидеть настоящую игру в браузере на настоящей цепочке.

**Веха 3. Лидерборд и `settle`** (§8), события (§9).

**Веха 4. Pyth Entropy** вместо заглушки: двухфазная разведка и спавны, моки в
тестах, liveness-fallback.

**Веха 5. Session-keys** и подключение кошелька (§10).

**Веха 6. Полный фронт**: переезд `../portal-lab/src/ui/*` на ончейн-состояние, локальная проекция
времени, UX async-состояний.

**Веха 7. Баланс и тюнинг** (§11.5, §11.6): сквозной забег до смерти, запись в
лидерборд, подкрутка чисел.

## 13. Журнал решений

Компактная карта, откуда взялся дизайн.

**Из первой версии SPEC:**

- Цель = buildanything на Monad; сеть = тестнет.
- Полностью ончейн — иначе не показывает Monad; растворяет анти-чит и доверие к
  серверу.
- Время идёт по `block.timestamp` — без живого времени выживалку нельзя проиграть.
- Pyth Entropy — детерминизм на публичном чейне равен предвидению.
- Диапазоны вместо тумана — storage публичен, спрятать записанное нельзя.
- Один режим — Pyth ⇒ недетерминизм ⇒ общий сид невозможен.
- Session-keys — real-time ончейн-игра иначе неиграбельна.
- Storage минимум плюс события — иначе «бесконечность» ончейн нежизнеспособна.
- `settle`-транзакция — лидерборд как чистое состояние контракта.
- Foundry плюс viem/wagmi; переиспользуем `../portal-lab/src/ui/*`.

**Добавлено в этой версии:**

- **Старение — формула, а не цикл.** Цикл не влезает в блок уже на пятиминутном
  отсутствии; и главное — формулу умеет посчитать фронт, а цикл нет.
- **Конец партии — только HP.** Правило «не действовал — забег закрыт» рассмотрено и
  отброшено: вместо запрета сделано следствие (§5.5).
- **Спавны от действий; длинная пауза детерминирована.** Иначе экран врёт до первой
  транзакции.
- **Цена у действий: ресурс, штат, порог нестабильности.** Иначе оптимальная
  стратегия — закрывать всё сразу, и игры нет.
- **Пять типов порталов; энергетический создаёт причину не закрывать портал.**
  Каскад рассмотрен и отклонён как вырождающийся в конвейер.
- **Спасение лечит HP** — при обязательном, проверяемом тестом условии баланса.
- **Арифметика в фиксированной точке; канон — Solidity; TS-зеркало обязательно**,
  потому что фронт всё равно обязан считать риск сам.
- **Параметры immutable, задаются при деплое.** Они участвуют в расчёте прошлого.
- **Веха 0 и тонкий срез подняты вперёд** — у ассистента нет доступа к сети, поэтому
  реальность приходит только на деплое.

## 14. Измерения

### 14.1. Веха 0 — сеть Monad testnet

**Условия замера:** контракт `Probe`

| Величина | Значение |
|---|---|
| Chain ID | 10143 |
| Время блока | ≈ 0,33 с (292 блока за 89 с) |
| Точность `block.timestamp` | 1 секунда |
| Лимит газа блока | 150 000 000 |
| Цена газа | ≈ 103 gwei (maxFee 138) |

| `tick()`, последующие | 34 728 газа → 0,00357 MON |

| Круг Remix → MetaMask → квитанция | ≈ 8 с на действие |

**Выводы:**

1. **Точность времени — секунда, а не блок.** Блоки 64138200, 64138201 и
   64138202 имеют одинаковый `block.timestamp` = 1789898885. При 15 с на игровой
   час контракт различает 15 отметок внутри часа; при 5 с было бы только 5, и
   деградация стала бы ступенчатой. Это аргумент за 15 с.
2. **Сеть не ограничивает темп.** Игровой час при 15 с — это ~45 блоков.
3. **Ограничивает кошелёк.** 8 секунд на действие через MetaMask — больше
   половины игрового часа. Без session-ключей игра физически неиграбельна;
   session-ключи (Веха 5) — обязательное условие, а не удобство.
4. **Замер «транзакции подряд» не получен.** Remix не отправляет следующую
   транзакцию, пока не получит квитанцию предыдущей. Замер переносится на Веху 5 —
   burner-ключ, шлющий напрямую.
5. **Переплаты из-за списания по лимиту не было:** `gasLimit` равен `gasUsed` во
   всех транзакциях, кошелёк ставит лимит ровно по оценке. Как только лимит начнёт
   задавать наш клиент, любой запас станет платой.
6. **Первая запись в нулевую ячейку в полтора раза дороже** (51 762 против
   34 728). Вместе с устройством storage Monad (страницы по 128 слотов, §3) это
   значит, что раскладка данных по слотам заметно влияет на цену действий. Учесть
   на Вехе 1.
7. **Деньги.** Игровое действие ожидаемо стоит порядка 0,01 MON; забег в пару
   сотен действий — порядка 2 MON. Burner-ключ заправляется ощутимо, а не «на
   копейку»; кран становится реальным ограничением для демо.

**Итог:** `SEC_PER_HOUR = 15` подтверждён. Окончательно — после замера задержки
колбэка Pyth на Вехе 4.

#### 14.2.3. Вывод про раскладку хранилища

Мы сложили `Game` и `Portal[12]` в одну структуру `Player` на четырнадцать
подряд идущих слотов, рассчитывая, что постраничный прогрев хранилища в Monad

**Измерения этого не подтверждают.** Цифры сети ложатся туда же, куда их
кладёт стандартная модель газа EVM. Единственное отклонение — `act` оказался
на 18% ниже локального минимума, но локальные замеры сняты на сценариях с
бо́льшим числом открытых порталов, поэтому отделить вклад прогрева от просто
меньшего объёма работы по этим данным нельзя.

Решение о компактной раскладке остаётся в силе: оно разумно само по себе. Но
обоснование, которое под него подводилось — постраничный прогрев Monad, — на
этой сети не проверено.

### 14.3. Ловушки, найденные на Вехе 0

- **Официальный шаблон Foundry от Monad содержит несуществующие ключи** `metadata`
  и `metadata_hash`. Foundry их молча игнорирует, `bytecode_hash` остаётся `ipfs`.
  Правильно: `bytecode_hash = "none"`, `cbor_metadata = true`. Проверено через
  `forge config`.
- **Remix 2.6.0 падает после деплоя на Monad** с ошибкой
  `Cannot read properties of undefined (reading 'result')`, причём транзакция в
  сети проходит успешно. Тумблер верификации ни при чём. Обход: взять адрес
  контракта в эксплорере и подключить его через «Deployed contracts → Add
  Contract». Из-за этого `Probe` задеплоен дважды.
- **Remix сериализует транзакции** — см. вывод 4.

## 15. Таблица результатов и фиксация счёта

### 15.1. Что считается результатом партии

Результат — два числа:

- **`hoursSurvived`** — игровой час гибели (`diedAtHour`), ключ ранжирования.
- **`creaturesRescued`** — сколько существ вышло живыми за партию, тай-брейк
  и смысловая мера.

Считается только существо, покинувшее портал живым по действию игрока. Это
единственный путь — `Action.Evacuate`. Гибель при обвале, гибель при закрытии
портала игроком (`Action.Close`) и существа, не спасённые при слепой эвакуации
(«один всегда остаётся в темноте»), в счётчик не идут.

### 15.2. Где хранится и кто может записать

**`mapping(address => BestRun) private _bestRun`** — постоянная запись в
хранилище контракта. Переживает `delete _players[player]` при `startGame`. Не
удаляется никогда.

```solidity
struct BestRun {
    uint32 hoursSurvived;     // ключ ранжирования
    uint32 creaturesRescued;  // тай-брейк
    uint32 settledAt;         // block.timestamp последнего обновления рекорда
    uint32 runsSettled;       // сколько завершённых партий записано
}
```

16 байт — один слот хранилища.

Записать может **кто угодно**: `settle(address player) public`. Никаких проверок
`msg.sender`. Это позволяет внешнему «будильнику» зафиксировать партию на
спящем игроке без его участия.

### 15.3. Семантика «лучшей попытки»

При каждом вызове `settle` / авто-settle:
- `hoursSurvived` новой партии **больше** записанного → перезаписываем всю
  тройку (`hoursSurvived`, `creaturesRescued`, `settledAt`).
- `hoursSurvived` **равны**, а `creaturesRescued` **больше** → перезаписываем.
- Иначе `hoursSurvived`/`creaturesRescued`/`settledAt` не меняем.
- `runsSettled` увеличивается на 1 **всегда**.

### 15.4. Когда и как происходит запись; порядок событий

**Явный вызов** — `settle(player)`:

  a. Партии нет → `revert NoGame()`.
  b. Уже зафиксирована → `revert AlreadySettled()`.
  c. Догнать мир до текущего часа (тот же `catchUp` из `act`/`sync`) —
     смерть могла наступить в отсутствие игрока.
  d. Партия всё ещё жива → `revert GameNotFinished()`.
  e. Записать итог, выставить `settled = true`; бросить `RunSettled` (и
     `GameOver`, если партия умерла именно в этом вызове — см. ниже).

**Авто-settle в `startGame`** — до `delete _players[player]`:

  - Партии нет или уже `settled` → пропустить.
  - Партия есть и не `settled` → догнать мир.
    - Если после догона партия **закончена** — записать итог, выставить
      `settled = true`; бросить события (см. ниже).
    - Если партия **ещё жива** — **не записывать ничего** (игрок бросил
      живую партию); бросить `GameForfeited` (см. §15.5).

#### Порядок событий

На всех трёх путях, где выполняется `catchUp`, события бросаются в одном
порядке:

  1. `PortalCollapsed` × N (все порталы, рухнувшие при догоне, N ≥ 0)
  2. `PortalSpawned`   × M (все порталы, появившиеся при догоне, M ≥ 0)
  3. `GameOver`           — только если партия умерла **именно в этом вызове**
  4. `RunSettled`         — только на путях `settle` и авто-settle

| Путь | `GameOver`? | `RunSettled`? |
|------|------------|--------------|
| `act` / `sync` | если умер здесь | — |
| `settle` | если умер здесь | всегда |
| авто-settle в `startGame` | если умер здесь | всегда |

**`GameOver` бросается ровно один раз за партию.** Флаг `game.finished`
читается до `catchUp`. Если партия уже была помечена завершённой в предыдущем
вызове (`sync` успел зафиксировать смерть), текущий вызов молчит. Это
позволяет `sync` брать смерть под отчёт, а последующему `settle` или
авто-settle не дублировать событие.

При **живом форфейте** (авто-settle нашёл незавершённую живую партию)
бросается только `GameForfeited(player, hoursElapsed)` — ни `GameOver`,
ни `RunSettled`.

### 15.5. Брошенная живая партия не ранжируется

Если игрок начинает новую партию, не дождавшись смерти предыдущей, старая
партия попадает в таблицу только если она успела умереть **до** вызова
`startGame`. Живая брошенная партия в таблицу не идёт.

**Почему:** иначе бросить партию на нулевом часу, вернуться через год и
получить `hoursSurvived = 8760` — это «выживание без риска». Такая запись не
имеет смысла.

### 15.6. Событие

```solidity
event RunSettled(
    address indexed player,
    uint32 hoursSurvived,
    uint32 creaturesRescued,
    bool newBest
);
```

Бросается один раз на каждую зафиксированную законченную партию. Фронт строит
таблицу из событий; сортировка — задача фронта. Никаких отсортированных структур
в storage нет.

### 15.7. Честность таблицы

Прежнее предупреждение («`RandomStub` предсказуем») **потеряло силу** и снято.
Проверено по коду: хэш `RandomStub.draw(player, nonce, salt)` нигде не вызывается;
от `RandomStub` остался только `inRange` — чистое отображение слова на диапазон.
Содержимое разведки и слепого захода выводится из слова Pyth, пришедшего после
фиксации ставки; сиды спавнов — из слова эпохи (§6.7).

Остаточные границы честности: мир известен игроку не дальше чем на `epochHours`
вперёд — игрок, вошедший в эпоху, может посчитать спавны до конца текущей эпохи,
то есть до 36 игровых часов (9 реальных минут) вперёд (осознанный компромисс,
Решение 1 версии 5), а сбой оракула стоит комиссии (§6.7).
